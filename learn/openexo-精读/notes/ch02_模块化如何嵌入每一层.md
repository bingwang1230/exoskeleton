# 模块化如何嵌入每一层

## 概念定义

模块化在 OpenExo 的落地三件套：①**软件** = 继承多态的类层级（整机→左右侧→关节→控制器/传感器/电机，计算自包含、被关节实例访问；多关节控制器定义一次处处可用）②**配置** = SD 卡构型文件（关节/侧、传动比、默认控制器、传感器使用、方向翻转、控制器参数；蓝牙 App 实时改参）③**电气** = CAN 总线（AK 系列换型号不动架构）+ 每侧 8-pin 传感器标准口。效果即设计目标 7：换硬件/控制不需要大改软件电气。

## 学习过程

@2026-08-31
- **初始理论**（上午在概念 1 时提出）：「高度模块化 → 接口简单 → 自由度减少」。
- **讨论演进**：面对 SD 卡方案，用户三段式回答——①逻辑上自由度仍减（全耦合代码表达力无限）②但真实基线是第三方组件，接口本就固定，OpenExo 把适配层配置化后自由度不变甚至更多 ③猜中间有接口协议/API 转接服务，接口复杂度体现在那。
- **三段全对，AI 锐化**：①指标应为「下一次变更的成本」而非表达力——耦合=表达力无限但每次改动贵；配置=表达力有界但改动便宜，设计赌注是 90% 实验室迭代落在预设词表内 ②「真实基线」洞察被确认——OpenExo 把「适配别人接口」的脏活做掉了 ③转接层=类层级+SD 配置语言+CAN/8-pin，接口复杂度由框架作者预付。
- **命名两个概念**：**抽象税**（接口/配置 schema/类层级的设计维护成本，NIH 预付一次，用户撞 schema 天花板时再付一次）与**双速系统**（配置=快车道分钟级，代码=慢车道天级；开源保证慢车道不锁死；nginx.conf vs fork 源码同构）。

## 关键洞察

- 自由度没有消失，是**从「改代码」搬到「改配置」**；搬不进配置的剩自由度留在代码慢车道。
- 抽象税总要有人付：作者付一次，撞天花板的使用者再付一次。
- ch1 脚手架句的兑现：付掉的账 = 抽象税（待用户回勾确认）。
