# 继承多态与层级(Exo→Side→Joint→控制器/传感器/电机)

## 概念定义

```
Exo                ← 整机
 ├─ ExoData        ⚠️ 数据镜像树(与计算树并排)
 ├─ Side[左]
 │   ├─ SideData
 │   └─ Joint[踝]
 │       ├─ JointData
 │       ├─ Controller*   ← 策略(可换:PJMC/PD/样条…)
 │       ├─ Motor*        ← 硬件代理人(AKMotor)
 │       └─ Sensor[]
 └─ Side[右]…
```

- **两种关系焊在一棵树**:Exo→Side→Joint 是物理拓扑镜像(**组合**);Joint 下挂的控制器/传感器/电机不是部位是能力(**策略**,基类指针 ⚠️推断)。
- **「计算自包含」双层含义**:①控制器不认识关节——接口只有「抽象关节状态→力矩」,髋踝差异(传动比/方向/参数)从控制器视野消失(搬去 SD 配置→概念 3);②数据自包含——值与行为解耦。
- **数据树/计算树镜像的硬理由**:Nano 只需打包数据、不需(也不该背)算法。数据+行为捆售会让 Nano 把整个 Joint 连算法编进固件;分开后 Nano 固件只含数据树,计算树只在 Teensy。**数据树=两颗芯片之间的契约**(UART 字节流=ExoData 快照)。
- 「一个多关节控制器定义一次即可被任何关节使用」= 策略模式+依赖倒置的回报;反面判据:控制器代码里出现 `if (joint == HIP)` 即抽象死亡。

## 学习过程

@2026-09-04

- **XML 直觉连接**:用户见镜像树即问「这不是另一个学习项目的 XML 结构么」——澄清未跳项目后确认其直觉撞到真东西:MuJoCo MJCF/URDF 同为 `整机→body→joint` 树形。**不是巧合:物理机构本身是树(部位嵌套+关节连接),问题结构决定数据结构,同一物理事实的多处投影**。C++ 类树是活的(算力矩),XML 是死的(纯描述等解释器)——「活树/死树」之分正好通向数据/计算分离的检验题。
- **彩蛋:嵌入式 OOP 纪律**(行业惯例非论文):对象开机一次 new 好,控制循环里绝不 new/delete——堆分配耗时不确定+碎片;服务器直觉「随用随建」在 600MHz 裸机上要收起来。
- **检验题(数据树为何单列)未答中**(0.6):用户猜「合在一起计算树没法抽象成函数/各关节各自实现输入输出」——仍在抽象框架打转,未用「几颗芯片/谁需要」提示。判卷后讲解 Nano 困境(只要账本不要会计;寄明信片≠搬邮局)。

## 关键洞察(金句)

- **组合长树,策略做插件**——两种关系焊在一棵树里
- **数据树是跨芯片契约,计算树是芯片私产**(数据树≈protobuf message 定义,UART 跑它的快照)
- **封装是捆售;当消费者对数据的需求不均,捆售从优点变障碍**(同构:protobuf/Redux/DTO)
- 嵌入式 OOP 多一条纪律:**开机建好一切,循环里只准调用,不准生长**
- 这棵架构的功夫全在「切」:算法与关节解耦(策略),值与行为解耦(契约)
- 活树(C++ 类)/死树(MJCF XML)同构于同一物理事实——写 P1 仿真 MJCF 时,是在给同一个东西写第二份描述

## 误解与纠正记录

| 原表述 | 判定/纠正 |
|---|---|
| 「把镜像树当成了另一个学习项目的 XML」 | 未跳项目;MJCF/URDF 同构是因物理机构本身是树 |
| 「合在一起计算树没法抽象成函数」 | ✗ 抽象(策略)与数据/计算分离无关;硬理由在 Nano 的处境:要数据、背不动行为 |
