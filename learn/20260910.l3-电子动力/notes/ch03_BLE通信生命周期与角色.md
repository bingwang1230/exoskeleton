# BLE 通信生命周期与角色（第 3 层：店的故事）

> 2026-11-03 开讲（L3 重排路线第 3 层；前置：板子三层、程序骨架、串行通信三条路均过关）。

## 概念定义

**【材料】**（BLE 通用模型 + 本课讲授；对照 ch03 课 §2 与 notes/ch03_BLE无线化双坑.md）

**通信一生五阶段（板子=店铺=外围设备 Peripheral）**：

```
广播（每100ms举牌喊名字exo-fsr，无数据）→ 连接（建专线，记连接句柄=客人号牌）
→ 订阅（客人说「有新货推给我」）→ notify（板子主动推数据行）
→ 断开（通道拆）→ 回广播等下一位
```

- **角色不对称（本层核心）**：外围设备只能广播等客，**协议里没有「主动找客人」的能力**；扫描/发起连接是中心设备（Central，谁跑收数脚本谁演：电脑 bleak / 手机 App）的事。重连=双边舞蹈：板子举牌+电脑 5s 看门狗重扫（实测 2-3s 恢复）。
- **板子主动做的全部三件事**：上电开始广播（出生段②③④段）、营业时每 10ms notify 推一行、断开时扔号牌（conn[0]=-1）+ 重新广播。广播态是唯一单向喊话；连接态是双向（数据推送+协议自动心跳）。
- **断开检测=心跳+监督超时**（supervision timeout，典型几秒【AI 补充】）：连接态双方按固定间隔互发包（无数据发空包），连续 N 个约会对不到→栈判死→抛 `_IRQ_CENTRAL_DISCONNECT` 事件进回调。板子不是「发进黑洞不知道」——用户首答此误解已纠正。
- **句柄匿名性**：板子只认客人编号（句柄），不知道对面是 MBP 还是手机→换收数端不改板子代码。互认靠 **MAC 地址+广播名**（出厂固化不怕重启）；本系统**未做配对/绑定**（无密钥互认，谁都能连，家用风险可接受【AI 口径待用户拍板】）。
- **单客设计**：协议与 NimBLE 支持多连接，但固件 `conn=[-1]` 单格+连接态停广播→一次一位。**实用推论：手机扫不到板子的第一嫌疑=电脑 fsr_live 还连着**（店铺有客不举牌）。
- **「固件双模」解密**：死循环里同一行 line 打印两遍——print 走 USB、notify 走无线电。bleak=装在 Mac 上的 Python 蓝牙客户端库（类比 requests 之于 HTTP）。

**代码映射（②③④⑤段）**：BLE()/active=开店；gatts_register_services=挂菜单（TX 格：READ+NOTIFY）；def _irq=值班员职责书（CONNECT 记号牌/DISCONNECT 扔牌+举牌）；**ble.irq(_irq)=排班**（坑一漏行）；gap_advertise=举牌；`if conn[0]>=0: gatts_notify`=有客才发货。

**conn 为什么是列表（第 3 层过关题，用户答对）**：函数内「查名字改对象」（`conn[0]=…`）顺外层引用共享改；「给名字赋值」（`conn=-1`）→ Python 判为局部变量 → 外层不动 → 症状与坑一相同且无报错。写错版本即坑一的孪生兄弟。

## 学习过程

@2026-11-03
- 讲解「店」类比五阶段；用户提问推进三轮：①重启后互认还在吗→拆 连接/配对/绑定 三词，本系统靠 MAC+名字；②「断开板子不知道、发黑洞」误解→心跳+监督超时纠正；③「板子会主动找 MBP」→角色不对称纠正（板子只会举牌）；④多连接问题用户自答正确（协议可多、我们单客写法+停广播）。
- 关闭题（conn 列表 vs 变量）：用户答「列表传值是引用，数值赋值只是函数内部局部变量」——核心机制正确，AI 补「查名字 vs 赋值名字」精确表述。

## 关键洞察

- 板子社交能力=举牌；所有主动性动作=三件（举牌/推数/扔牌再举牌）。
- 换收数端零改板码的根因=句柄匿名性。
